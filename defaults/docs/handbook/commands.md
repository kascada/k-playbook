# Commands

Compact index of slash commands. Detailed flows are on dedicated topic pages; this page does not duplicate them.

Shipped review recipes come from the hub (`<hub>:k-playbook/defaults/reviews/`, read as `k-playbook:/reviews/…`); the shipped commands and skills are unpacked by the binary into `~/.local/share/k-playbook/` and linked through `.k-playbook/share` (source in the repo: `share/`). Project-owned review recipes, instructions and includes live in the project collection under `keph:/k-playbook/` (task 143), project-owned guidelines under `keph:/docs/guidelines/` (task 148), project-owned commands and skills under `.k-playbook/commands/` and `.k-playbook/skills/` in the project root, the directory holding `.k-playbook/K-PLAYBOOK.yaml`. There are no checks any more, neither shipped nor project-owned (task 155). There are no configured paths anymore.

A project-owned command with the name of a shipped command **replaces** it; an empty one disables it. This page lists the shipped commands; the assistants section in the interface shows what actually applies in a particular project.

## Review flow

`<ergebnisort>` stands for the location of review results. It is not decided yet; reviews are paused until then.
`/k-review`, `/k-audit` and `/k-remediation` are temporarily unavailable, and all five review tools of the MCP server are blocked. The code-review family is deliberately staged:

| Occasion | Command | Result |
|---|---|---|
| complete security sweep across suitable tools and audit recipes | `/k-audit` | `<ergebnisort>/YYYY-MM-DD/review-input.json`, `review-input.md`, `review-triage.md` |
| focused individual review recipe, interactive or as a report | `/k-review <name>` | interactive change proposals or `<ergebnisort>/<family>/YYYY-MM-DD/review-input.json` and `review-triage.md` |
| harden a task/instruction file before execution | `/k-task-refine [ref-or-path] [nochmal]` | review log directly in the reviewed task/instruction file |

1. `/k-review <name>` runs a recipe and, depending on the recipe, produces interactive change proposals or `review-triage.md` as a report handoff.
2. `/k-audit` orchestrates the run model: creates or continues a run, starts scanners, runs evidence recipes before the merge, starts the merge, leads perspectives afterward, and writes `review-triage.md`.
3. `/k-remediation <result>` plans how to address findings. It takes exactly one result file; merging happens exclusively in the audit run.

When `/k-remediation` creates tasks, they belong in the normal task flow: first `/k-task-refine`, then `/k-task-run`.

## Task flow

```text
/k-task-create
/k-task-refine

```

Tasks arise directly from the conversation or from `/k-remediation`. In both cases, they are reviewed before execution.

## Where commands find their targets

No command reads or guesses a path. Every target is a `keph:` reference into the project collection or lies under `.k-playbook/` in the project root, the directory holding `.k-playbook/K-PLAYBOOK.yaml`:

| Command | writes to |
|---|---|
| `/k-task-create`, `/k-task-run` | `keph:/user/<user>/tasks/` in the project collection, completed tasks to `done/` below it (`k_playbook_doc_done`); nothing on disk. `/k-task-run` also keeps one ref `refs/k-task-run/<task>` per task in the execution root until the task moves to `done/` |
| `/k-todo` | `todos/` in the project collection, written only through `k-playbook todo` or the MCP tools |
| `/k-review`, `/k-audit` | `<ergebnisort>`; both commands are paused |
| `/k-docs-code`, skill `ks-overlay-repo-analyse` | `keph:/docs/generated/code/` in the project collection, only through `k-playbook docs publish code`; in between the machine-local working directory `.k-playbook/work/docs/code/` with the checkout record next to it (`/work` is git-ignored), removed after a complete publish together with `.k-playbook/work/docs/` and `.k-playbook/work/` when they are left empty. `/k-docs-code` also writes the split documentation orders, one per document, to `keph:/queue/docs/`; closed orders move to `keph:/queue/docs/done/` |

| `/k-docs alle` | besides what the producers write, the `README.md` under `keph:/docs/` that are missing or differ from their templates, through `k-playbook docs readme` |

| `/k-befunde-einordnen` | the run protocol `keph:/queue/einordnung/<NNN>-<datum>-<sitzung>.md` (kind `einordnung`, one list item `- <full name> \| <target or reason>` per finding handled or skipped — the full names are a deliberate, temporary exception to the rule that nothing refers into `keph:/queue/`; only the closing message refers to the protocol), the targets listed above, `keph:/queue/unclear/`, and deletions in `keph:/queue/findings/`; changed project files stay uncommitted |

It additionally reads what is shipped: recipes through `k-playbook:` references from the hub, scripts from `~/.local/share/k-playbook/scripts/`. It never writes there.

## The resolved working state

No command determines what applies itself. The tool does that:

```bash
k-playbook context
```

The JSON output names the resolved directories, remediation policy, and the catalog `reviews`, with shipped and project-owned reviews already merged; a catalog `checks` no longer exists (task 155):

```json
{
  "catalogs": {
    "reviews": [
      { "name": "review-code.md",  "key": "code",  "origin": "dist" },
      { "name": "review-tech.md",  "key": "tech",  "origin": "override" },
      { "name": "review-api.md",   "key": "api",   "origin": "local" },
      { "name": "review-sast.md",  "key": "sast",  "origin": "override",
        "disabled": true }
    ]
  }
}
```

`origin` is `dist`, `local`, or `override`. `disabled` appears where the project-owned file is empty; that is how to disable a shipped entry.

The call occurs at the beginning of every command, but only once per session. Its output does not change during work and is the same for every command, so subsequent commands reuse it. It is retrieved again when `K-PLAYBOOK.yaml` has been written, the inventory of reviews has changed, or work has moved to another project.

`/k-review` works on this set and displays it before working. The detailed rules are in [`k-playbook-format.md`](./k-playbook-format.md#merge-shipped-and-project-owned-content).

There is no check runner any more: `k-check` and the shipped checks were removed in task 155.
